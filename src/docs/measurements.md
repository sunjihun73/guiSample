### 2026-09-17 RAG 검색 튜닝 (top-k / similarityThreshold / hnsw.ef_search)
- 배경: distance-type 변경(COSINE→INNER_PRODUCT 등)은 검색 품질 레버가 아님.
  OpenAI 임베딩은 단위벡터라 cosine/inner-product/L2 의 순위가 수학적으로 동일.
  게다가 기존 HNSW 인덱스가 vector_cosine_ops 라 바꾸면 인덱스를 못 타고 full scan 이 된다.
- 유사도 실측 (318 청크, text-embedding-3-small, 1 - cosine_distance):
  | 질의 | 최고 유사도 | 성격 |
  |------|------------|------|
  | "pgvector 도커 실행 방법 알려줘" | 0.477 | 정답 문서 |
  | "테오리아 행성은 어디에 있나"    | 0.286 | 정답 있으나 검색 실패 |
  | "오늘 점심 메뉴 추천해줘"        | 0.305 | 무관(노이즈 상한) |
- 결론: 노이즈 floor 0.25~0.31, 정답 0.477. → threshold 0.35 채택.
  통념적인 0.5 를 썼다면 유일한 정답 문서(0.477)까지 잘려 RAG 가 침묵했을 것.
- 적용: top-k 4→8, similarityThreshold 없음→0.35 (SpringAiConfig),
  hnsw.ef_search 40(기본)→100 (spring.datasource.connection-init-sql, 양 프로파일).
- 미해결: "테오리아" 는 코퍼스에 존재하는 고유명사인데 최고 0.286 으로 노이즈와 구분 안 됨.
  dense 임베딩의 고유명사 약점 → 하이브리드 검색(tsvector+RRF) 또는 3-large 재인덱싱 후보.
- 중복 인덱스 정리 완료: vector_store_embedding_idx DROP.
  두 인덱스는 정의가 완전 동일(hnsw / embedding / vector_cosine_ops, reloptions 없음, 각 2552kB, 319 pages).
  Spring AI 2.0.0-M4 가 소유하는 이름은 spring_ai_vector_index (CREATE INDEX IF NOT EXISTS, 클래스 상수 확인)
  이므로 initialize-schema 가 재생성하는 쪽을 남기고 구버전 자동명명 잔재를 제거했다.
  되돌리려면: CREATE INDEX vector_store_embedding_idx ON vector_store USING hnsw (embedding vector_cosine_ops);
  총 크기 8.2MB → 5736kB.
- 발견(중요): 현재 코퍼스 318 청크에서는 플래너가 HNSW 를 아예 안 쓴다 — seq scan 2.8ms 가
  강제 index scan 15.3ms 보다 빠르기 때문(정상 동작). 즉 hnsw.ef_search 설정은 지금은 no-op 이고,
  코퍼스가 커져 인덱스를 타기 시작할 때 효과가 난다. 인덱스 자체는 유효함(enable_seqscan=off 로 확인).
  → 지금 단계의 검색 품질은 전적으로 임베딩 모델·청킹·threshold 가 좌우한다.

### 2026-09-17 임베딩 모델 교체 (text-embedding-3-small → 3-large@1536)
- 차원 결정: 네이티브 3072 불가. pgvector 0.8.3 HNSW 는 2000 차원이 상한
  ("column cannot have more than 2000 dimensions for hnsw index" 실측 확인).
  → MRL 절단으로 dimensions=1536 사용. 스키마·인덱스·pgvector.dimensions 무변경.
  LiteLLM 이 dimensions 파라미터를 그대로 통과시키는 것 확인(1536 요청 → 1536 응답).
- 재색인: 318 청크를 shadow 컬럼(embedding_new)에 재임베딩 후 컬럼 스왑.
  원문 파일이 아니라 vector_store.content 를 재임베딩했으므로 청킹 경계는 그대로다.
- 검색 품질 비교 (상위 1건 유사도):
  | 질의 | 3-small | 3-large@1536 | |
  |------|---------|--------------|---|
  | pgvector 도커 실행 방법 | 0.477 | **0.667** | 정답, 큰 개선 |
  | 테오리아 행성 | 0.286 | **0.372** | 정답 청크가 top-3 에 처음 진입(0.356) |
  | 라인하르트의 부관 | 0.477 | 0.464 | 사실상 동률, top-3 구성은 3-small 이 약간 나음 |
  | 오늘 점심 메뉴(노이즈) | 0.305 | **0.244** | 노이즈 하락 = 분리도 개선 |
  | 김치찌개(노이즈) | 0.245 | 0.247 | 동일 |
- 결론: 신호 0.477→0.667 상승, 노이즈 0.305→0.244 하락. 신호/노이즈 분리도가 확연히 개선.
  단 "라인하르트의 부관" 처럼 소설 서사 질의는 개선 없음 — 균일한 개선이 아니다.
- threshold 재조정: 0.35 → 0.32 (노이즈 상한 0.247 과 최약 정답 0.356 사이).
  threshold 는 임베딩 모델 종속이므로 모델 교체 시 반드시 재측정.
- 비용: 3-large 는 3-small 대비 약 6.5배($0.02 → $0.13 / 1M tokens).
  현재 볼륨(누적 $0.042)에서는 무시 가능하나 대량 색인 시 재검토.
- 롤백: 구 벡터는 vector_store.embedding_3small_backup 컬럼에 보존돼 있다.
  되돌리려면 컬럼을 다시 스왑하고 인덱스를 재생성한 뒤 yaml 을 3-small 로 되돌릴 것.
  롤백이 불필요해지면: ALTER TABLE vector_store DROP COLUMN embedding_3small_backup;
